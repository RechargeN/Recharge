# ADR 0023: Три вида аккаунта — User (он же Creator), Professional Page, Admin

- Status: **Accepted** (решение владельца продукта 2026-11-06, включая ответы на
  OQ-1–OQ-3 — раздел «Решения владельца»). Принятие задаёт целевую модель; код,
  схемы, правила и облако меняются только отдельным срезом реализации.
- Date: 2026-11-06
- Deciders: владелец продукта
- Supersedes: ADR 0015 §2, §3, §4 и перечень ролей в §6;
  утверждения «Persisted roles remain User, Creator and Admin» в ADR 0016,
  ADR 0017 и ADR 0021 §1. Остальные части этих ADR сохраняются.
- Related: ADR 0013, ADR 0015, ADR 0016, ADR 0017, ADR 0021,
  `docs/product/IDENTITY_PUBLISHER_SLICE_SPEC.md`,
  `docs/product/IDENTITY_PUBLISHER_BACKEND_SPEC.md`,
  `docs/product/BACKEND_IDENTITY_PUBLISHER_COVERAGE_MATRIX.md`

## Context

По ADR 0015 системных ролей три: `User`, `Creator`, `Admin`. `Creator` выдаётся
только после отдельной проверки личности; «Pro» — это `Creator` плюс членство в
Professional Page. ADR 0021 уже объединил интерфейс: у каждого аккаунта один
личный профиль под названием Creator, но техническая роль `Creator` по-прежнему
требует проверки.

Владелец продукта формулирует модель иначе: три вида аккаунта —
**User (он же Creator)**, **Professional Page** и **Admin**. Отдельной ступени
«User → проверенный Creator» в продукте быть не должно.

На dev (N2c, 2026-11-06) сервер выдаёт новому аккаунту только `User`; Creator и
Admin клиентом или провайдером не выдаются. Эта граница сохраняется при любой
модели: роль и права выдаёт только сервер.

## Decision

### 1. Три вида аккаунта

| Вид | Что это | Кто выдаёт |
|---|---|---|
| **User** (он же Creator) | Любой вошедший аккаунт. Смотрит, участвует, создаёт и публикует от личного имени | Сервер при первом входе (Google/Apple) |
| **Professional Page** | Компания, организация, площадка, частный профессионал; публикует от имени страницы; владелец мест (Place) | Создаёт User; публикует после проверки страницы сервером |
| **Admin** | Персонал Recharge: модерация, проверки, поддержка | Только сервер/процедура персонала |

### 2. User = Creator

Отдельной глобальной роли `Creator` нет. Любой `User` с активным аккаунтом может
создавать и публиковать личный контент через personal publisher
(`PublisherRef{type: user}`), в пределах прав (capabilities) по типам контента,
модерации и ограничений частоты.

Проверка личности перестаёт быть входом в публикацию и становится
**необязательным фактом доверия** (значок «Профиль подтверждён»), который
требуется для рискованных возможностей — решение OQ-2.

### 3. Professional Page — контекст публикации и владения

Professional Page (`ManagedPage`) остаётся отдельным агрегатом с
членством (owner/manager) и правами, привязанными к конкретной странице.
Владение местом (Place owner) — это проверенная страница, заявившая права на
Place, а не свойство пользователя.

Professional **не является глобальной ролью** (решение OQ-1): права одной
страницы не дают доступа к другой; требование ADR 0015 §6 сохраняется.

### 4. Admin без изменений

`Admin` — служебная роль. Не выдаётся пользователю, не даёт ни членства в
страницах, ни публикации от их имени. Предпросмотр опыта (ADR 0017) остаётся.

### 5. Неизменные гарантии

- Роль, права, членство и проверки выдаёт только сервер; клиентский
  интерфейс не является источником прав.
- `PublisherRef{type, id}` и явный выбор «Публиковать как» (ADR 0015 §5)
  сохраняются.
- Проверка страницы и факт проверки личности — независимые серверные факты с
  аудитом.

## Решения владельца (2026-11-06)

- **OQ-1 → членство.** Три вида аккаунта — продуктовая модель. Технически
  глобальные роли только `User` и `Admin`; Professional Page — членство
  (owner/manager) в конкретной странице с правами этой страницы. Глобальной
  роли `Professional` нет.
- **OQ-2 → бесплатный личный контент сразу.** User публикует бесплатный личный
  контент без проверки личности — с модерацией и ограничениями частоты. Платное,
  бронирование мест, аренда и сбор денег — только от проверенной Professional
  Page или при серверном факте проверки личности.
- **OQ-3 → `Creator` читается как `User`.** Реальных Creator на dev нет. Старое
  значение `Creator` в записях и ответах читается как `User`; агрегат
  `CreatorVerification` становится фактом проверки личности (значок и условие
  для рискованных возможностей из OQ-2), без отдельной роли.

## Поправка владельца (2026-11-08): правило маркетплейса

Заменяет вторую половину OQ-2 («платное — только при проверке личности»).
Основа — DSA ст. 30 (прослеживаемость продавцов), DAC7 и KYC платёжного
провайдера; формат — как у маркетплейсов (Etsy, Vinted).

- Обычный бесплатный контент публикуется без полной проверки личности.
- Платное или юридически значимое бронирование нельзя опубликовать или
  активировать, пока автор не указал статус «частное лицо / trader»,
  контакты и (для trader) регистрационные данные — **декларация продавца**.
  Бесплатная внутренняя регистрация на событие юридически значимым
  бронированием не считается.
- Trader, если договор заключается внутри Recharge (оплата или бронирование в
  приложении), проходит проверку личности **до начала продаж**, а не перед
  выплатой (DSA ст. 30).
- Перед первой выплатой обязательно завершается KYC/KYB платёжного провайдера и
  подтверждается счёт. Выплат пока нет; любой будущий путь выплаты обязан
  спрашивать `PayoutReadinessPort` (сейчас всегда «не готово»).
- Данные DAC7 собираются отдельно по типу деятельности (личные услуги, аренда
  вещей), без универсального порога.
- При подозрении на мошенничество Trust & Safety включает досрочную step-up
  проверку: пока флаг стоит, любое платное или бронируемое требует проверки
  личности.
- Срок хранения реквизитов trader после удаления аккаунта (DAC7/налоги) —
  решение юриста; до него декларация удаляется вместе с аккаунтом (PB-01).

## Consequences

Затрагивает (оценка по `rg`, 2026-11-06): Identity-схемы `packages/api_contracts`
(6 файлов, перечисление ролей `User|Creator|Admin`), backend Identity/Publisher и
Content (21 файл, включая `creator_verification_service`,
`publisher_eligibility_service`, `access_snapshot_service`), mobile (14 файлов:
права, workspace, Create Hub), правила Firestore, спецификации
Identity/Publisher, раздел ролей в `AGENTS.md`, `LAUNCH_STATUS.md`.

Изменение затрагивает права публикации, поэтому реализация идёт отдельным
срезом после принятия: контракт → сервер (выдача прав) → правила → клиент →
тесты отказов (чужая страница, неподтверждённая страница, Admin без членства).
Принятие этого ADR само по себе не разрешает изменения в облаке.

## Alternatives considered

- **Оставить модель ADR 0015** (User/Creator/Admin с обязательной проверкой
  личности для публикации) — не соответствует продуктовой модели владельца.
- **Глобальная роль Professional** — отклонена владельцем (OQ-1): смешивает
  права разных страниц.
