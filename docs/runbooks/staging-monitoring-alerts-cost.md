# Staging: мониторинг, оповещения и контроль расходов

Статус: **Draft, проверен на staging 2026-11-17 (N4e).** Относится к `recharge-staging-y9y2y`; для dev действует то же, кроме нагрузочного входа. Числа бюджета ошибок — из `BACKEND_SERVICE_RELIABILITY_SLO_MODEL.md`; **для staging приняты владельцем 2026-11-17** (99,9 % доступности, p95 1,5 с для команд и 750 мс для чтения, период 28 дней). Для production BCK05-OD-03 остаётся Proposed.

## Что есть и чего нет

| | Состояние |
|---|---|
| Бюджет | €5 в месяц на проект, пороги 50/75/90/100 % фактических расходов, письмо и сообщение в Pub/Sub |
| Канал | один e-mail владельца на проект |
| SLO | 5 на сервисе `recharge-stage-functions`: доступность входа, команд и чтения (99,9 %), задержка команд (95 % ≤ 1,5 с) и чтения (95 % ≤ 750 мс), 28 дней (с 2026-11-17) |
| Синтетические пробы | `*-probe-booking` (создание брони), `*-probe-booking_read` (чтение брони), `*-probe-session` (вход): POST с недействительным токеном раз в 5 минут из трёх регионов; ожидается 401 **с телом приложения** `"UNAUTHENTICATED"` — отказ фронтенда Google пробу не пройдёт |

**Уровни и письма (решение владельца 2026-11-18, dev и staging одинаково):**

| Уровень | Политики | Письмо владельцу |
|---|---|---|
| Critical | `*-probe-failed` (критичная функция не отвечает больше чем в одном регионе 10 мин); `*-slo-fast-burn` (доступность входа, команд или чтения: 5xx/429 в 10 раз быстрее допустимого за час) | да: при открытии и при восстановлении, одно письмо на событие |
| Warning | `*-slo-latency-fast-burn`, `*-slo-slow-burn`, `*-slo-budget-50/75-percent-spent`, `*-telemetry-absent`, `*-server-errors`, `*-media-tools-failure` | нет: инцидент виден в Cloud Monitoring → Alerting |
| Финансы | бюджет €5 на проект, 50/75/90/100 % фактических расходов | да (письмо Google Billing) |
| Служебное | `*-budget-channel-delivery-test` | только при ручной проверке доставки |

`*-telemetry-absent` считает метрику по функции целиком (сумма по ревизиям): новая выкатка больше не выглядит как «нет метрики».
| Автоматическое ограничение расходов | **нет**: сообщение бюджета никто не обрабатывает |

**Оповещение бюджета — уведомление, а не ограничитель.** Оно приходит с задержкой в часы (расходы нагрузочного прогона 16.11 через два часа ещё не попали в сообщение бюджета) и ничего не останавливает.

## Что реально ограничивает расходы

1. **Лимиты функций:** у всех функций 1 экземпляр и 1 одновременный запрос. Это ограничивает скорость расходов, но не сумму: функция, занятая круглосуточно, — около €55 в месяц, и записи Firestore сверху.
2. **Лимиты запросов на пользователя** (`security/abuse_policy.ts`) и список разрешённых uid.
3. **Выключатели** (ниже).
4. **Отключение биллинга** — крайняя мера, только решением владельца: может уничтожить данные. Автоматически не выполняется.

## Выключатели

| Выключатель | Что делает | Как включить | Время до эффекта |
|---|---|---|---|
| Создание Booking (`N4C_BOOKING_CREATE_DISABLE`) | новые Booking получают `feature_disabled`; отмена, подтверждение и чтение работают | `python -I n4c_cloud.py kill-on`, вернуть — `load-off` | около 1 мин 50 с (проверено 2026-11-17) |
| Кодбаза целиком (`*_ENABLED=false`) | все функции кодбазы отвечают 503 | повторная выкатка кодбазы с выключенным runtime | 2–3 мин (проверено в N4a) |
| Нагрузочный вход (`N4C_LOAD_ENABLED`) | закрыт по умолчанию; открыт только на время прогона | `load-on` / `load-off` | 2 мин |

Выключатель — это повторная выкатка того же кода с другим `.env`, а не флаг в базе: цель «эффект за 2 минуты (p95)» выдерживается на пределе и зависит от доступности Cloud Build. Выключатели Operations в базе работают только на Emulator.

Сдерживание расходов никогда не блокирует отмену Booking, чтение и обязательные операции приватности (`backend-cost-response.md`).

## Окна бюджета ошибок и скорость сгорания

Период — 28 дней, бюджеты по маршрутам не объединяются.

| Маршрут | Цель | Бюджет ошибок | Задержка |
|---|---:|---:|---|
| Вход и Session | 99,9 % | 0,1 % | p95 ≤ 750 мс, p99 ≤ 2 с |
| Команды, включая Booking | 99,9 % | 0,1 % | p95 ≤ 1,5 с, p99 ≤ 3 с; при распродаже популярного пула — p95 ≤ 5 с (решение владельца 2026-11-17), такая распродажа расходует бюджет задержки команд |
| Свои данные (чтение) | 99,9 % | 0,1 % | p95 ≤ 750 мс, p99 ≤ 2 с |
| Уведомления: старт доставки | 99,5 % | 0,5 % | p95 ≤ 60 с |

| Сигнал | Условие | Действие |
|---|---|---|
| Быстрое сгорание | ≥ 10× допустимой скорости за 1 ч, подтверждено окном 5 мин | остановить выкатки, разобрать как инцидент |
| Медленное сгорание | ≥ 2× за 24 ч, подтверждено окном 2 ч | задача с владельцем, пересмотр выкатки |
| Израсходовано 50 % бюджета | любой маршрут | не расширять доступ и рискованные флаги |
| Израсходовано 75 % | любой маршрут | только работы по надёжности |
| Бюджет исчерпан | остаток ≤ 0 | обычные выкатки остановлены до плана восстановления |
| Нарушение инварианта (перепродажа мест, чужие данные) | одно подтверждённое событие | немедленное сдерживание, независимо от скорости сгорания |
| Нет телеметрии | трафик есть, сигнала нет 10 мин | инцидент мониторинга; «зелёным» не считать |

На staging трафик почти нулевой, поэтому знаменатель SLO в основном дают пробы (их 401 — хороший ответ), а сгорание при единичных ошибках легко превышает пороги: на staging быстрое сгорание означает «посмотреть журнал», а не «инцидент».

Заведено (2026-11-17): быстрое и медленное сгорание для всех пяти SLO, отказ пробы больше чем в одном регионе, журнальное оповещение о серверных сбоях. Подтверждение «коротким окном» сделано выдержкой условия (5 мин и 2 ч), а не вторым условием: в политике не больше 6 условий. Пороги 50/75 % израсходованного бюджета и «нет телеметрии» оповещениями **не** заведены — смотреть вручную на странице SLO.

### План восстановления бюджета (записан 2026-11-24)

Основание: правило «Бюджет исчерпан → обычные выкатки остановлены до плана восстановления» (таблица выше) и находка O1 B-03. Числа — из Cloud Monitoring (`select_slo_budget_fraction`, `select_slo_counts`, суточные окна), чтение 2026-11-24 ~00:30 UTC.

Суточная разбивка — по окнам, выровненным на момент чтения: дата означает «примерно эти сутки».

**Причины (разбор журналов 2026-11-23, итог дня)**

- 18.11 07:14–08:03 — **наши uptime-проверки** били в `createInternalBooking` и `getMyBooking`, пока бронь была выложена закрытой (сразу после N4e round 1): ~66 плохих событий, основная часть минуса команд и чтения staging.
- 13.11 21:25–21:32 и 22.11 12:46 — **пробы скриптов выкладки** (Python-urllib) в закрытые функции: ожидаемые 503 «закрыто», засчитаны как плохие. Сюда же отказы входа 13–14.11 и 22.11.
- 06.11 (dev, вход) — пробы первой выкладки N2c.
- 19.11 19:17 — **один настоящий отказ пользователю**: A34 → `contentQueryV1` 500 «aborted after waiting too long for an available instance». Причина: `maxInstances 1` и `concurrency 1` — параллельные запросы приложения ждали единственный экземпляр.
- Ошибки плановых задач 19.11 и 21.11 («нужен индекс / индекс строится») в SLO доступности не входят; после достройки индексов их нет.

Вывод: бюджеты сожгли в основном служебные пробы; реальный риск для пользователя один — очередь в один запрос.

**Когда восстановится (прогноз, если новых плохих событий не будет)**

Трафик сейчас ~900 событий в сутки на SLO (в основном пробы, их 401 — хороший ответ), поэтому допустимое число плохих растёт по мере заполнения окна.

| Проект | SLO | Остаток ≥ 0 примерно с | За счёт чего |
|---|---|---|---|
| staging | вход | 2026-12-03 | рост знаменателя; 13 событий 13–14.11 выходят из окна 11–12.12 |
| staging | команды | 2026-12-16 | 33 события 18.11 выходят из окна |
| staging | чтение | 2026-12-16 | то же |
| dev | вход | 2026-12-04 | 15 событий 06.11 выходят 04.12 |
| dev | команды | 2026-11-24 | рост знаменателя |
| dev | чтение | в норме | — |

Прогноз пересчитывать перед каждой выкладкой в staging (правило плана пробелов: перед выкладкой проверять все три бюджета доступности).

**Что считается выкаткой** (останавливается при остатке ≤ 0): код или конфигурация функций (включая concurrency, maxInstances, память), образы сканера и обработчика, Firestore Rules, TTL и индексы, включение семейств и флагов, изменение IAM рантайма. **Не считается:** документы, правка каналов и текста оповещений, чтение журналов и метрик, синтетические пробы без записи.

**Что разрешено до восстановления**

- Только работы по надёжности и безопасности, каждая — строкой в «Исключения из остановки выкаток» с решением владельца (первая — RC захода 1, выше).
- Расширение доступа, новые семейства функций, рискованные флаги — нет, до восстановления или отдельного решения владельца.

**Чтобы служебные пробы больше не жгли бюджет**

- Скрипты выкладки не пробуют закрытые функции «живыми» запросами: проверка закрытия — чтением конфигурации и журналов; если проба нужна, то в открытую функцию и с ожидаемым 401.
- Uptime-проверки направлены только на функции, открытые в этой выкладке; перед закрытием семейства — сначала пауза проверки.
- Учёт: каждая плановая проба, давшая плохое событие, записывается в журнал выкладки с числом событий.

## Порядок действий

**Письмо бюджета (50/75/90/100 %).**
1. Открыть отчёт биллинга, найти сервис и проект — сообщение бюджета отстаёт на часы.
2. Если расходы растут из-за Booking — `kill-on`; из-за другой кодбазы — выключить её runtime.
3. Проверить, что нагрузочный вход закрыт и лимиты 1/1 (чтение конфигурации функций).
4. Записать решение: продолжать, сократить или остановить.
5. Отключение биллинга — только явным решением владельца после проверки сохранности данных.

**Письмо `stage-slo-fast-burn`, `stage-slo-slow-burn`, `stage-probe-failed` или `stage-server-errors`.**
1. Пробы всех функций недействительным токеном: ожидается 401; 503 — runtime выключен или сбой.
2. Журнал запросов за 15 минут (`n4b_logs.py`): статус и задержка по сервисам.
3. Последняя выкатка: если сбой начался после неё — вернуть прежний RC тем же скриптом (dev раньше staging).
4. Подозрение на перепродажу мест или чужие данные — сразу `kill-on` и разбор.

**Проверка доставки оповещений (раз в 7 дней, после смены канала и после создания политики — не раньше чем через 5 минут: новая журнальная политика начинает действовать не сразу).**
1. Записать пробную запись в журнал `stage-budget-channel-test`.
2. Владелец подтверждает письмо.
3. Прочитать свежее сообщение бюджета из Pub/Sub.
