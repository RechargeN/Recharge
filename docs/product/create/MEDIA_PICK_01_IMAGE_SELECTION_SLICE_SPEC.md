# MEDIA-PICK-01 — выбор изображения в Create

Статус: **Done** — реализовано (`7061a5c`), проверено на Samsung A34 и принято владельцем 2026-11-04; решения §12 приняты как предложено. Версия 0.3: уточнения реализации в §6 и §7 (поправка 1).
Источник: B1-device на Samsung A34 (2026-11-03): пункт scope «реальные
permissions и выбор изображения» не проверяем, потому что в приложении нет
выбора изображения ([evidence](../../verification/B1_DEVICE_ACCEPTANCE_2026_11_03.md)).

Приоритет: Accepted ADR → эта спека → LAUNCH_STATUS. Связанные документы:
`docs/architecture/PLATFORM_FOUNDATION_SPEC.md` (picker adapter, sanitation,
PF-AC-20), `docs/architecture/FIREBASE_ARCHITECTURE.md` §12.2 (клиент сжимает
и удаляет метаданные), `docs/product/MEDIA_D1_REAL_TOOLS_AMENDMENT.md` §4.5
(лимиты обработчика), `docs/product/MEDIA_STORAGE_BACKEND_SPEC.md`.

## 1. Проблема

Обложка и галерея в Create — текстовые поля «URL / путь» (`MediaEntity
.coverImage`, `.gallery`). Пользователь телефона не может выбрать фото из
галереи или камеры: на A34 обложку для C3 пришлось подложить файлом через
стенд. Без этого не закрывается B1-device и не работает реальный путь
Creator → Media.

## 2. Цель

Пользователь выбирает изображение системным выбором (и, по решению MP-OD-02,
камерой) в каждой Create-форме, где есть обложка или галерея. Приложение
сохраняет **только нормализованную копию без метаданных** в своей приватной
папке и записывает её локальный путь в то же поле черновика. Дальше всё
работает как сейчас: валидация черновика, upload через `EventCoverSource` /
Media-адаптеры, обработчик на сервере.

## 3. Границы

В scope:

- платформенный picker через порт (`RouteGpxFilePickerPort`-подобный
  `CreateImagePickerPort`) и адаптер в `lib/app/adapters`;
- нормализация на клиенте (§5) в отдельном use case, вне UI;
- приватное хранение копий черновика и их очистка (§6);
- общий виджет выбора для cover и gallery, подключаемый в существующие
  секции form engine (не отдельный флоу на тип; правило 4 AGENTS.md);
- коды ошибок, сообщения en/ru/lv, accessibility;
- тесты (§10) и пункт B1-device на A34 с оператором.

Не в scope: обрезка/редактор, фильтры, видео, несколько файлов за один выбор
(если MP-OD-06 не решит иначе), облачный upload и Storage (существующие
gated адаптеры не меняются), изменение серверного обработчика и его лимитов,
AI-описание изображений, распознавание лиц/контента, iOS-проверка на
устройстве (отдельная среда).

## 4. Где появляется выбор

Существующие поля, без новых полей и без изменения схемы черновика:

| Create-тип | Обложка | Галерея |
|---|---|---|
| Event | да (обязательна) | да |
| Place | да (по policy типа) | да, ≤ 12 |
| Activity | да (обязательна) | да |
| Class / Workshop | да | да |
| Bookable Session | да | да |
| Route | да (обязательна для публикации) | — |
| Find People | да (необязательна) | — |
| Типы без своего блока (общая media-секция `CreatePage`, например Rental, Collection) | да | да |

Поле URL/путь остаётся в debug-сборке для тестов стенда; в release его
видимость решает MP-OD-04.

## 5. Нормализация (клиент)

Вход — то, что вернул платформенный picker (JPEG, PNG, WebP, HEIC/HEIF и
т. п.). Выход — один файл, который проходит текущую политику обработчика
(`MEDIA_D1_REAL_TOOLS_AMENDMENT.md` §4.5: JPEG/PNG/WebP, ≤ 1 048 576 Б,
≤ 6000 × 6000):

1. Платформа уменьшает изображение до длинной стороны `maxEdge` (MP-OD-03,
   предложение 2048 px) и, если нужно, конвертирует HEIC/HEIF в JPEG
   (`image_picker` `maxWidth/maxHeight/imageQuality`).
2. Клиент декодирует результат в пиксели, применяет EXIF-ориентацию к
   пикселям и **заново кодирует в JPEG без метаданных**: ни EXIF, ни GPS,
   ни XMP/ICC-профилей устройства, ни имени исходного файла. Шаг 1 метаданные
   не убирает надёжно (Android-ресайзер копирует часть EXIF), поэтому шаг 2
   обязателен.
3. Если файл больше `maxBytes` (1 048 576 Б), качество снижается ступенями
   (85 → 75 → 65), затем длинная сторона 1600 px; не уложилось —
   `media_too_large`.
4. Анимация, несколько страниц, повреждённые и пустые файлы → отказ
   (`media_unsupported` / `media_decode_failed`). Прозрачность PNG
   заливается белым при переходе в JPEG (MP-OD-07 может выбрать PNG/WebP).
5. Работа выполняется в отдельном isolate; UI показывает прогресс и
   отмену; таймаут 20 с → `media_decode_failed`.

Исходный файл и платформенная ссылка (URI, путь кэша) не сохраняются, не
попадают в черновик, telemetry, логи или publish payload
(`PLATFORM_FOUNDATION_SPEC.md`). Сервер по-прежнему проверяет сигнатуру,
декодирование и лимиты сам; клиентская нормализация — не граница доверия.

## 6. Хранение и очистка

- Копия пишется в `getApplicationSupportDirectory()/create_media/<draft
  localId>/<ULID>.jpg` атомарно (temp + rename); в поле черновика — этот
  путь.
- Замена обложки или удаление изображения из галереи удаляет прежний файл
  после сохранения черновика.
- Поправка 1 (2026-11-04, при реализации): в локальном (mock) потоке
  опубликованная версия ссылается на тот же путь, поэтому удаление после
  публикации, при удалении черновика, при смене аккаунта и sweep «сирот»
  сейчас удалили бы изображения опубликованных объектов. В этом slice копия
  удаляется только при замене обложки и удалении фото из галереи, а
  недописанные `.jpg.tmp` — перед каждым выбором. Полная очистка — follow-up
  MEDIA-PICK-02 вместе с серверной финализацией Media.
- Квота: не больше 13 файлов на черновик (1 + 12) и 64 МиБ на все черновики;
  сверх — `media_storage_full`.

## 7. Permissions

- Android 13+: системный Photo Picker, разрешение на чтение медиа **не
  запрашивается и не объявляется** (`READ_MEDIA_IMAGES` нет в manifest).
  Android ≤ 12: системный выбор документа, тоже без разрешения на хранилище.
- Камера (если MP-OD-02 = да): `image_picker` вызывает системное приложение
  камеры; разрешение CAMERA приложению не нужно и не объявляется. Если
  платформа требует разрешение, отказ пользователя даёт понятное сообщение и
  ссылку в настройки, без повторного навязчивого запроса.
- iOS: `NSPhotoLibraryUsageDescription` и `NSCameraUsageDescription`; PHPicker
  не требует полного доступа к библиотеке (`requestFullMetadata: false`).
  Поправка 1: строки пока английские, как уже существующие строки
  геолокации; локализация всех описаний разрешений (`InfoPlist.strings`
  ru/lv в Xcode-проекте) — вместе с проверкой iOS, когда будет среда.
- Проверка на A34: реальный системный выбор, отсутствие запроса разрешений
  (gallery), отказ и повторный выбор камеры по MP-OD-02.

## 8. Архитектура

- Domain: `CreateImagePickerPort` (`pick(source) → PickedImage?`, где
  `PickedImage` — байты и тип, без путей) в
  `features/create/domain/repositories`; `NormalizeCreateImageUseCase` и
  `CreateMediaStore` (сохранить/удалить/sweep) за интерфейсами.
- Data: `FileCreateMediaStore` (support directory, атомарная запись).
- App adapter: `ImagePickerCreateImageAdapter` (`image_picker`), регистрируется
  в DI рядом с GPX picker.
- Application: методы контроллера `pickCover`, `addGalleryImage(fromPicker)`,
  `removeGalleryImage` вызывают use case и обновляют существующие поля.
- Presentation: общий `CreateMediaPicker` для cover и gallery внутри
  существующих секций; ключи виджетов стабильны для тестов
  (`create-media-pick-cover`, `create-media-pick-gallery`).
- Boundary gate: новых исключений нет; plugin используется только в
  `lib/app/adapters`.
- Kill switch: локальный config-флаг `create.mediaPicker` (по умолчанию —
  MP-OD-05); выключенный флаг возвращает текущее поведение (поле пути).

## 9. Ошибки и тексты

| Код | Когда | Текст (en; ru/lv в ARB) |
|---|---|---|
| (нет) | пользователь закрыл выбор | ничего не показывается |
| `media_unsupported` | анимация, несколько страниц, неизвестный формат | «This image can't be used. Choose a photo.» |
| `media_decode_failed` | файл повреждён или не открылся за 20 с | «This image couldn't be opened. Try another one.» |
| `media_too_large` | не уложилось в лимит после сжатия | «This image is too large even after compression.» |
| `media_storage_full` | квота черновиков | «Not enough space for draft photos. Remove some photos.» |
| `media_permission_denied` | платформа отказала в доступе (камера) | «Allow camera access in Settings to take a photo.» |

Коды регистрируются в каталоге сообщений L4 и в контракте «схема ↔ каталог».
Сообщения никогда не показывают код.

## 10. Тесты

- Unit: нормализатор на фикстурах — JPEG с EXIF/GPS/ориентацией 6, PNG с
  прозрачностью, HEIC-эквивалент (после платформы — JPEG), 12-МП фото,
  анимированный WebP, обрезанный файл: выход ≤ 1 048 576 Б, ≤ `maxEdge`,
  **ни одного EXIF/XMP/GPS маркера**, ориентация применена к пикселям,
  отказы с верными кодами.
- Unit: `FileCreateMediaStore` — атомарная запись, замена, удаление, sweep
  сирот, квота, смена аккаунта.
- Widget: cover/gallery в Event, Place, Activity, Route через fake-порт:
  выбор, отмена, ошибка, удаление, лимит галереи 12, kill switch off.
- Stand (PC host): C3 через выбор (fake-порт отдаёт фикстуру) → upload →
  модерация → публикация; обработчик принимает файл.
- B1-device (A34, оператор): системный выбор из галереи, запрос разрешений
  отсутствует, камера по MP-OD-02, файл в приватной папке без EXIF/GPS
  (`run-as` + проверка байтов), C3 с выбранной обложкой до публикации,
  `am kill` во время нормализации не оставляет битых файлов.
- Gates: `flutter analyze`, `flutter test`, boundary, diff-check, затронутые
  stand gates (C3, D3.x, J2) на одном SHA.

## 11. Критерии приёмки

1. MP-AC-01: во всех формах §4 обложку можно выбрать системным выбором; в
   галерее — добавить до лимита типа.
2. MP-AC-02: сохранённый файл — JPEG (или формат по MP-OD-07) ≤ 1 048 576 Б,
   ≤ `maxEdge`, без EXIF/GPS/XMP; ориентация верная.
3. MP-AC-03: исходник и платформенная ссылка нигде не сохраняются; telemetry
   и логи не содержат путей и имён файлов.
4. MP-AC-04: на Android запрос разрешения на чтение медиа не появляется;
   manifest не объявляет `READ_MEDIA_IMAGES`/`READ_EXTERNAL_STORAGE`.
5. MP-AC-05: замена обложки и удаление фото из галереи удаляют прежнюю
   копию; недописанные файлы не остаются (поправка 1; остальная очистка —
   MEDIA-PICK-02).
6. MP-AC-06: все ошибки §9 показываются текстом на en/ru/lv, без кодов.
7. MP-AC-07: kill switch off возвращает прежнее поведение без потери
   черновиков.
8. MP-AC-08: существующие черновики с URL/путём продолжают работать без
   миграции.
9. MP-AC-09: C3 stand gate проходит с выбранной обложкой; серверный
   обработчик принимает файл без изменений своих лимитов.
10. MP-AC-10: пункт B1-device «реальные permissions и выбор изображения»
    пройден на A34 с оператором.

## 13. Миграция и откат

Схема черновика не меняется: поле хранит строку пути, как сейчас. Откат —
kill switch off или откат коммита; уже сохранённые копии остаются валидными
локальными путями и удаляются sweep после удаления черновиков. Сервер и
Storage не меняются.
