## Вопрос 1 — Доступ Viewer к локальному authoring

`VISION.md` разрешает Viewer (без Creator-статуса) локальный
pre-verification draft для личного Scenario — без Submit/Publish. Rental,
наоборот, всегда требует Creator (аренда — полукоммерческое предложение).
Recharge Activity по природе ближе к личному, самостоятельному контенту, чем
к Rental, но формально пока не отнесена ни к одному из прецедентов.

**Варианты:**
- **A. Разрешить, как у personal Scenario** — Viewer может сохранить
  локальный draft Activity без Submit/Publish; отправка на публикацию
  по-прежнему требует Creator capability.
- **B. Требовать Creator всегда**, как у Rental — без исключений для Viewer.

**Рекомендация:** A — Activity ближе по природе к личному Scenario
(самостоятельное, не коммерческое), чем к Rental; отказ Viewer в локальном
черновике не защищает ни от чего, чего не защищает уже сам гейт
Submit/Publish.

**Ответ: A** — принято по рекомендации. Применено в §9 спеки.

## Вопрос 2 — Лимит на неофициальные (`accessCaution.isInformal`) точки от одного Creator

Без ограничения ничто не мешает одному Creator массово размещать точки на
частной/неофициальной территории без модерационной проверки — риск как для
пользователей (небезопасные/незаконные маршруты), так и для продукта
(жалобы, репутация).

**Варианты:**
- **A. Без отдельного лимита** — общий rate-limit и report/moderate поток
  считаются достаточными.
- **B. Soft-порог** — например, 3 активные `isInformal = true` карточки от
  одного Creator; дальше — предупреждение и ручная проверка следующих, без
  блокировки публикации.
- **C. Hard-порог** — жёсткая блокировка публикации сверх лимита без
  явного одобрения модератора.

**Рекомендация:** B — тот же принцип, что уже принят для Collection
(«честный автор с несколькими законными точками не должен получать
блокировку», см. Вопрос 3 в
`COLLECTION_GUIDE_CREATE_BLOCK_OPEN_QUESTIONS.md`), но с вниманием: здесь
цена ошибки выше (реальная безопасность посетителя, не просто спам-контент).

**Ответ: B, порог = 3** — принято по рекомендации. Применено в §12/§15.1
спеки: 4-я и последующие активные `isInformal = true` карточки от одного
Creator не блокируются (`entityStatus` остаётся `published`), но получают
`moderationStatus = flagged_for_review` для приоритетной ручной проверки.

## Вопрос 3 — Владение решением о расширении флага `A` на другие категории

Сейчас флаг `A` (Activity разрешена) несут пять категорий каталога (§8
спеки: `wellness_recharge`, `outdoor_nature_walking`, `sport`,
`water_activities`, `winter_seasonal`, плюс единичное исключение
`parkour`). У Rental — свой закрытый whitelist, отдельный от каталога; у
Activity такого whitelist нет, флаг живёт прямо в `CATEGORY_SYSTEM.md`.

**Варианты:**
- **A. Category System владеет целиком** — расширение флага `A` решается
  обычным governance-процессом `CATEGORY_SYSTEM.md` §11 («добавление
  подкатегории — свободно, данные»), без отдельной Activity-специфичной
  политики или ревизии этого документа.
- **B. Этот документ вводит собственный контролируемый whitelist**, как у
  Rental — расширение требует отдельной ревизии
  `RECHARGE_ACTIVITY_CREATE_BLOCK_SPEC.md`.

**Рекомендация:** A — Activity спроектирована намеренно без собственного
whitelist (в отличие от Rental, см. §7 спеки), поэтому дублировать
категорийное governance здесь избыточно и создаёт два источника истины.

**Ответ: A** — принято по рекомендации. Применено в §8 спеки. Расширение
флага `A` решается через `CATEGORY_SYSTEM.md` §11, без отдельной ревизии
этого документа.

## Вопрос 4 — Отдельная CTA «Report a problem with this spot»

Спека сейчас полагается на общий report/block механизм платформы. Для
`accessCaution`-точек (неофициальные, потенциально проблемные) может быть
ценна более заметная, специфичная по формулировке CTA.

**Варианты:**
- **A. Общий report/block механизм достаточен** — без нового UI-элемента.
- **B. Отдельная CTA** с явной формулировкой повода («Проблема с доступом к
  этому месту») — заметнее для `accessCaution`-точек, но вводит исключение
  из общего паттерна, которого нет у других 9 типов Create Hub.

**Рекомендация:** A на старте — не создавать новый UI-паттерн без
подтверждённого спроса; если после запуска жалобы по informal-точкам
покажут отдельную кластеризацию, вынести B отдельным slice с метриками в
руках.

**Ответ: A** — принято по рекомендации. Применено в §17.3 спеки. Общий
report/block механизм остаётся единственным путём в v1; отдельная CTA —
кандидат post-MVP при подтверждённом спросе.

## Вопрос 5 — Эскалация модерации при завышенном `optionalContribution.amountHint`

Валидация §12 спеки проверяет только форму поля (`note` обязателен при
заданном `kind`), не добросовестность использования. Теоретически
`kind = donation` с завышенным `amountHint` может стать скрытым способом
обойти отсутствие формального тарифа (§2 инвариант).

**Варианты:**
- **A. Без отдельной эскалации** — полагаемся на общий report/жалобы
  пользователей post-hoc.
- **B. Автоматический soft-порог по сумме** — `amountHint` выше некоторого
  значения (абсолютного или относительно типичного для категории/страны)
  помечает объект для обязательной ручной проверки перед публикацией.
- **C. Явный moderator playbook без нового технического порога** —
  модератор получает чёткий критерий («donation ощутимо выше типичного
  доната по региону = вероятный скрытый тариф, отклонить/запросить
  уточнение»), но проверка остаётся ручной по report, не автоматической.

**Рекомендация:** C — вводить числовой автоматический порог без
статистики по реальным заявкам преждевременно; playbook для модератора
можно зафиксировать сразу, а B рассмотреть, если после запуска
накопятся данные о злоупотреблении.

**Ответ: C** — принято по рекомендации. Формулировка playbook зафиксирована
в §19 спеки.

## Вопрос 6 — Связь с будущей editorial-подборкой уровня города (Collection/Guide)

Позиционирование Recharge Activity изначально обсуждалось как «после
работы, показать людям места по городу» (например, курируемый набор точек
для Резекне). Технически это пересекается с типом Collection/Guide (#10 в
`VISION.md`), у которого уже есть открытые вопросы о том, как формируются
пункты подборки (`COLLECTION_GUIDE_CREATE_BLOCK_OPEN_QUESTIONS.md`,
Вопрос 10 про area-приоритизацию — напрямую обслуживает этот сценарий).

**Варианты:**
- **A. Collection — курируемый список ссылок на существующие Activity/Place
  объекты**, без собственного контента сверх заметки куратора
  (`curatorNote`) — согласуется с уже принятой моделью
  `ItemsPickerSection` в Collection-спеке.
- **B. Отдельный редакционный слой** со своим «городским гидом», не
  построчно привязанным к объектам каталога — гибче для редакции, но
  дублирует часть данных, которые уже есть в самих Activity-объектах.

**Рекомендация:** A — Collection уже спроектирована именно под этот
сценарий (ссылки + куратор-заметка); создавать параллельную модель под
конкретно «recharge по городу» избыточно. Ответ на этот вопрос стоит
координировать с ответом на Вопрос 10 в
`COLLECTION_GUIDE_CREATE_BLOCK_OPEN_QUESTIONS.md`, а не решать изолированно.

**Ответ: третий вариант, не A и не B** — Recharge Activity получает
**собственный отдельный слой обнаружения** (dedicated discovery layer):
не только категорийный фильтр внутри общего Search/Map, а выделенная,
всегда живая поверхность именно для `activity`-объектов — параллельно
Collection, не вместо неё. Collection остаётся ручной editorial-курацией
(«гид по городу от редакции»); новый слой — алгоритмический, live,
не требует ручной сборки куратором. Детали зафиксированы в §16 спеки
(§16.1 «Отдельный слой обнаружения»). Связь с Collection (Вопрос 10 в
`COLLECTION_GUIDE_CREATE_BLOCK_OPEN_QUESTIONS.md`) остаётся актуальной —
это не взаимоисключающие механизмы: город может иметь и живой слой
Activity, и отдельно курируемый Collection-гид поверх него.
