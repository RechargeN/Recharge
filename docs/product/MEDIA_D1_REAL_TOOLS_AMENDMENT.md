### 3.2 Что именно ставит npm

У `sharp` с 0.35 нет install-скрипта, но npm **скачивает платформенные
optional-пакеты с готовыми нативными бинарниками**: на win32-x64 это № 6. Lock
получает 30 новых записей: № 5–10 и 24 платформенных пакета (darwin, linux,
linuxmusl, freebsd, webcontainers, win32-ia32/arm64), включая
`@img/sharp-linux-x64` 0.35.5 и `@img/sharp-libvips-linux-x64` 1.3.4 с их SRI —
они на Windows не скачиваются, но нужны Linux-проверке. № 9 и № 10 будут
скачаны: у `@img/sharp-wasm32` нет ограничения `os`/`cpu`, и npm (arborist
`optionalSet`) не удаляет его вместе с пропущенными freebsd/webcontainers.
`sharp` может загрузить эту WASM-сборку, если нативная не загрузилась;
processor этого не допускает — без нативной привязки `@img/sharp-win32-x64`
ответ `failed`, актив остаётся в карантине.

`%LOCALAPPDATA%\Recharge\tools\_rejected\<время>\` для проверки владельцем.
Архивы распаковываются только после проверки SHA-256 и центрального каталога

ссылок и точек повторной обработки; при распаковке байты считаются, превышение
объявленного размера записи прерывает распаковку. Свободно на диске 43,8 ГБ.

1. **Node** (№ 1): скачать, SHA-256, проверить каталог, распаковать в

### 3.4 Почему в манифесте Node.js

Закреплённый в `toolchain.lock.json` npm 10.9.8 на этом PC повреждён: во всех
трёх переносных копиях в `%TEMP%` нет `node_modules/npm/lib/commands`
(вероятно, очистка временных файлов Windows). `node.exe` цел — SHA-256 совпадает
с официальным. Регрессы F1/F2 запускали npm-скрипты через npm 10.8.2 из
`C:\Program Files\nodejs` с Node 22.23.2 — для запуска скриптов это не важно,
для изменения lock — важно, поэтому lock меняется только восстановленным
10.9.8. Новая копия лежит вне `%TEMP%`.

### 3.5 Базы сигнатур ClamAV: условия и тестовая база стенда

Условия использования официальных баз не опубликованы: в документации
(FAQ, раздел CVD, раздел Signatures) и на `clamav.net/about` указана только
GPL для движка и CC BY-ND 2.5 для содержимого сайта. Поэтому манифест
согласуется **с оговоркой** и одним из вариантов:

- **L1 (рекомендую).** Локально официальные базы не скачиваются; `clamd`
  загружает только тестовую базу стенда (ниже). Локально доказывается работа
  движка, `INSTREAM`, разбора архивов, эвристик `Broken.Media`/`Limits.Exceeded`
  и всего пути отказа — с тестовой сигнатурой. Официальные базы, `freshclam`,
  свежесть реальной базы и EICAR переходят в Linux gate; до их использования
  владелец решает вопрос условий. Контроль свежести при L1 — §7: отсутствие
  официальной `daily` никогда не считается пройденным контролем.
- **L2.** Владелец явно принимает неопубликованные условия для внутренней
  локальной проверки: базы не распространяются, не зеркалируются, не попадают
  в репозиторий. Тогда № 11 с бюджетом 400 МБ и свежестью по §7.

**Тестовая база стенда (L1).**

- Состав: один файл `recharge-stand.ndb` с одной сигнатурой
  `Recharge.Test.Marker:0:*:<hex>`, где `<hex>` — шестнадцатеричная запись
  безобидной ASCII-строки `RECHARGE-D1-STAND-MARKER-NOT-MALWARE`. Строка —
  константа в `media_tool_limits.ts`; сам файл в репозиторий не кладётся.
  Это собственный файл проекта, сторонних условий у него нет.
- Поставка: `media-tools.mjs fetch` вычисляет файл из константы и записывает
  его SHA-256 в `media-tools.lock.json` (`databases.stand`). `start` пишет файл
  в пустой каталог `clamav-run\db`, сверяет SHA-256 с lock и проверяет, что в
  каталоге баз ровно этот файл; любое расхождение или лишний файл — отказ
  запуска.
- Проверка загрузки после старта `clamd`, обе пробы через `INSTREAM`, маркер
  только в памяти:
  - положительная: буфер с маркером → `FOUND` с именем
    `Recharge.Test.Marker` (ClamAV добавляет к неофициальным сигнатурам
    суффикс `.UNOFFICIAL`; точная форма сверяется на установленной сборке);
  - отрицательная: буфер без маркера → `OK`.

  Иначе — отказ запуска, сервис не принимает заявок.
- Ответ `VERSION` при L1 не содержит версии официальной `daily` — это
  состояние `absent` контроля §7.

## 4. Сервис инструментов и лимиты ресурсов

### 4.1 Почему отдельный сервис

Functions-эмулятор в режиме AUTO держит пул runtime-процессов на каждую
функцию и добавляет новый процесс, когда все заняты
(`RuntimeWorkerPool.getIdleWorker`/`addWorker`, firebase-tools 15.28.1).
Пул и очередь внутри runtime-процесса поэтому умножились бы на число процессов.
Отсюда один **локальный сервис инструментов** на loopback, который запускает
и останавливает `scripts/media-tools.mjs`:

- адаптеры `ScannerPort` и `ProcessorPort` в Functions — тонкие клиенты
  (`local_tools_client.ts`, `node:http` к `127.0.0.1`, без keep-alive, с
  токеном запуска); `sharp` и libvips в runtime Functions не загружаются;
- сервис держит **глобальный** приём заявок (§4.3), пересылает сканирование в
  `clamd` и обрабатывает изображения в одном дочернем процессе-обработчике;
- конвейер изображений, протокол `clamd`, протокол сервиса и лимиты — чистые
  модули в `src/modules/media/infrastructure/`; хост сервиса и обработчик —
  стендовый код в `test/stand/`; запуск, остановка и самопроверка —
  `scripts/media-tools.mjs`.

### 4.2 Потолок памяти: держатель job

Механизм — **Windows Job Object** с флагами `JOB_OBJECT_LIMIT_PROCESS_MEMORY`,
`JOB_OBJECT_LIMIT_JOB_MEMORY`, `JOB_OBJECT_LIMIT_ACTIVE_PROCESS`,
`JOB_OBJECT_LIMIT_DIE_ON_UNHANDLED_EXCEPTION` и
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`.

Для каждого процесса (`clamd`, сервис) `media-tools.mjs` запускает
**держателя** — Windows PowerShell с встроенным C#-классом (§3.8). Держатель:

1. создаёт именованный job (`Local\recharge-media-<роль>-<экземпляр>`) с
   лимитами и помещает в него себя;
2. запускает процесс через `Start-Process -NoNewWindow` — процесс и все его
   дочерние процессы рождаются внутри job, окна без лимита нет;
3. держит дескриптор job, пока процесс жив, и выходит вместе с ним.

Закрытие держателя (штатная остановка, падение, завершение) закрывает
последний дескриптор, и `KILL_ON_JOB_CLOSE` завершает все процессы job —
сиротских процессов не остаётся. Пока держатель жив, имя job открывается для
проверок (`status`, `selftest`).

| Job | На процесс | На job | Процессов | Состав |
|---|---|---|---|---|
| сервис | 768 MiB | 1 GiB | ≤ 3 | держатель, сервис, обработчик |
| `clamd` | 1 GiB (2 GiB при L2) | 1,25 GiB (2,25 GiB при L2) | ≤ 2 | держатель, `clamd` |

Новый обработчик запускается только после подтверждённого выхода прежнего;
иначе лимит процессов не даст его запустить, и задача получит `failed`.

Сервис принимает заявки только после команды готовности от
`media-tools.mjs`, которую тот посылает, убедившись через `IsProcessInJob`,
что держатель и сервис в job. Если job не создан или процесс не в нём —
запуск отменяется, адаптеры отвечают `failed`/`inconclusive` (fail-closed).

Остаточный риск, записанный явно: лимит Job Object — это лимит выделенной
(committed) памяти; при его достижении выделение отказывает, и обработчик или
`clamd` завершаются с ошибкой → `failed`/`inconclusive`. Держатель
(PowerShell, около 65 MiB) входит в бюджет job. Runtime-процессы
Functions-эмулятора не ограничиваются — `sharp` и `clamd` в них не
загружаются. На Linux эквивалент (cgroup или `prlimit`) — часть Linux gate.

### 4.3 Приём заявок: немедленный ограниченный отказ

| Очередь | Одновременно | Ожидают | Предел ожидания | Сверх этого |
|---|---|---|---|---|
| обработка | 1 | ≤ 2 | 5 с | сразу `503 busy` → process `failed` |
| сканирование | 2 (= `MaxThreads` `clamd`) | ≤ 4 | 5 с | сразу `503 busy` → scan `inconclusive` |

Очереди — массивы фиксированной длины, без растущих цепочек промисов. Заявка,
пролежавшая дольше срока, получает отказ. HTTP-сервер:
`maxConnections` = 11 (лишние соединения закрываются сразу), обязательный
`Content-Length` ≤ `maxBytes`, `headersTimeout` 2 с, `requestTimeout` 10 с.
Повторы ограничены существующей политикой `maxProcessingAttempts` = 3.

### 4.4 Форматы и загрузчики

- Разрешены только JPEG, PNG, WebP (неподвижные). Тип определяется по первым
  байтам (как сейчас) **и** по `metadata().format` после разбора заголовка;
  оба должны совпасть с объявленным, иначе `rejected`.
- В обработчике все загрузчики libvips блокируются
  (`sharp.block({ operation: ['VipsForeignLoad'] })`), затем разблокируются
  ровно три буферных загрузчика JPEG/PNG/WebP (`sharp.unblock`). Точные имена
  операций сверяются на установленной сборке; тест доказывает, что SVG, GIF,
  TIFF, HEIF, PDF и JXL отклоняет сам обработчик даже в обход проверки байтов.
- `unlimited: true` не используется никогда (статический тест §10).

### 4.7 Обработчик: таймауты и изоляция

- Дочерний процесс сервиса; один; `sharp.concurrency(1)`, `sharp.cache(false)`;
  обязательна нативная привязка (§3.2).
- `sharp.timeout({ seconds: 8 })` на каждый конвейер; жёсткий срок сервиса —
  15 с на задачу. По истечении сервис завершает обработчик, задача — `failed`,
  следующий запуск поднимает новый процесс (внутри того же job). Падение или
  выход обработчика → `failed`.
- Перезапуск после 100 задач. Ответ обработчика проверяется по схеме и
  ограничен по размеру; неверный ответ → `failed`.

### 4.10 Протокол сервиса

HTTP/1.1 только на `127.0.0.1`, без keep-alive (`Connection: close`).
Типы, заголовки, лимиты и проверка ответов — общий модуль
`local_tools_protocol.ts` для клиента и хоста.

- Доступ: `Authorization: Bearer <token>`; токен — 32 случайных байта на
  каждый запуск, хосту передаётся через окружение, эмулятору — через
  `RECHARGE_MEDIA_TOOLS_TOKEN` от D1-gate, хранится в файле состояния
  запуска. Без верного токена — `401`. Команды управления требуют отдельного
  токена управления, который есть только у `media-tools.mjs`.
- Запросы с телом: обязательные `Content-Length` ≤ `maxBytes`,
  `Content-Type: application/octet-stream`, `X-Recharge-Request-Id`,
  `X-Recharge-Sha256`. Хост пересчитывает SHA-256 тела; расхождение — `400`.
  Объявленный тип не передаётся: тип определяется по байтам и формату после
  разбора, а объявленный уже сверен в `confirmUpload`.

| Метод и путь | Тело | Ответ |
|---|---|---|
| `GET /v1/health` | — | `200` `{schemaVersion:1, state:'starting'\|'ready'\|'degraded'\|'draining', instanceId, toolRevision:{scanner, processor}, database:{state:'fresh'\|'stale'\|'absent', daily?, builtAt?, exemption?}, queues:{scan:{active, waiting}, process:{active, waiting}}, worker:{pid}\|null}` |
| `POST /v1/scan` | байты | `200` `{schemaVersion:1, result:'clean'\|'rejected'\|'inconclusive', toolRevision, signature?, reason?}` |
| `POST /v1/process` | байты; `X-Recharge-Profiles` | `200` `{schemaVersion:1, result:'succeeded'\|'rejected'\|'failed', toolRevision, transformProfileRevision, variants?:[{profile, format:'webp', width, height, byteLength, sha256, bytesBase64}], reason?}` |
| `POST /v1/control/arm` | — | `204`; только токен управления; после проверки членства в job |
| `POST /v1/control/drain` | — | `202`; новые заявки — `503 draining`, начатые доводятся до конца или до срока |

Коды отказа: `503` `{reason:'busy'\|'not-ready'\|'draining'}` с `Retry-After`;
`413` — больше `maxBytes`; `400` — неверные заголовки или SHA-256; `401`.

Клиент (`local_tools_client.ts`): соединение ≤ 2 с; весь вызов scan ≤ 20 с,
process ≤ 25 с (срок обработчика 15 с плюс передача); ответ ≤ 1,2 МБ, иначе
обрыв; ответ проверяется по схеме; для каждого варианта клиент сам
пересчитывает SHA-256 и длину по байтам и только потом пишет его через
`ObjectStorePort.writeVariant`. Любая ошибка клиента → scan `inconclusive`
или process `failed`.

### 4.11 Запуск: `media-tools.mjs start`

1. Предусловия: Node 22.23.2 в `tools` с проверенным SHA-256 `node.exe`;
   SHA-256 распакованных файлов ClamAV совпадают с записанными при `fetch`;
   SHA-256 тестовой базы совпадает с lock (L1); нет записанного живого
   экземпляра (иначе отказ); свободные порты на `127.0.0.1`.
2. Пишутся `clamd.conf`, каталог баз, токены доступа и управления.
3. Держатель K1 запускает `clamd` в job `clamd` (§4.2). Ожидание `PING`→`PONG`
   ≤ 60 с; `VERSION`; при L1 — положительная и отрицательная пробы §3.5.
4. Держатель K2 запускает хост сервиса в job `сервис`; хост стартует в
   состоянии `starting` и заявок не принимает.
5. Проверка: K1 и `clamd`, K2 и хост — в своих job (`IsProcessInJob`); лимиты
   job совпадают с §4.2 (`QueryInformationJobObject`).
6. `POST /v1/control/arm`; хост запускает обработчика; `health` →
   `ready`, PID обработчика — в списке процессов job `сервис`.
7. Записывается файл состояния
   `%LOCALAPPDATA%\Recharge\tools\run\state.json`: для каждого процесса PID,
   время старта, путь; имена job; порты; путь к файлу токенов; ревизии
   инструментов; состояние базы.

Любая ошибка на шагах 1–6 → остановка всего уже запущенного (§4.12) и выход
с ошибкой; файл состояния не пишется.

`status` читает файл состояния, проверяет идентичность процессов, лимиты и
состав job, `health`; ничего не меняет.

### 4.12 Остановка: `media-tools.mjs stop`

1. Чтение файла состояния; для каждого процесса сверяются PID, время старта и
   путь — при расхождении (PID переиспользован) отказ без действий, как в
   `emulator-stand.mjs`.
2. `POST /v1/control/drain`, ожидание завершения начатых заявок ≤ 20 с.
3. Завершение держателя K2 → `KILL_ON_JOB_CLOSE` завершает хост и обработчик;
   затем K1 → `clamd`.
4. Проверка: ни одного записанного PID, job `сервис` и `clamd` не
   открываются, порты закрыты.
5. Файл состояния переименовывается в `state.stopped-<время>.json`
   (не удаляется).

Процессы, которых нет в файле состояния, не трогаются никогда.

### 4.13 Отказы и восстановление

| Отказ | Что видит Media | Восстановление |
|---|---|---|
| сервис не запущен или порт закрыт | scan `inconclusive` / process `failed` → карантин | `start`, затем повтор finalize → `ready` |
| `clamd` недоступен при живом сервисе | scan `inconclusive`; `health` → `degraded` | `stop` и `start` |
| обработчик превысил срок, упал или упёрся в лимит памяти | process `failed`; сервис жив | новый обработчик для следующей задачи |
| сервис упал | соединение отклонено → `inconclusive`/`failed`; держатель K2 выходит, job закрывается, обработчик завершён | `status` показывает `down`; `stop` подтверждает исчезновение процессов и переименовывает состояние; `start` |
| держатель упал или завершён | `KILL_ON_JOB_CLOSE` завершает процессы его job; дальше как выше | то же |
| очередь заполнена | сразу `503 busy` → `inconclusive`/`failed` | повтор по `maxProcessingAttempts` |
| неверный токен | `401` → `inconclusive`/`failed`; ошибка конфигурации в журнале | перезапуск D1-gate |
| база `stale` или `absent` без исключения стенда | scan `inconclusive` (§7) | L1: исключение только через D1-gate; L2: обновление баз решением владельца |
| эмулятор запущен без переменных сервиса | прежние заглушки | — |
| неизвестный режим в переменных | Media не запускается (fail-closed) | исправить запуск |

## 5. SVG

SVG исключён fail-closed на трёх уровнях: нет в списке типов политики; проверка
первых байтов не распознаёт `<svg` и `<?xml` как изображение
(`signature_mismatch`); обработчик отказывает любому формату вне JPEG/PNG/WebP,
загрузчик SVG заблокирован. Санитайзер не нужен и не добавляется.

## 6. EXIF/GPS

Сначала применяется ориентация (`autoOrient`), затем выход пишется **без**
метаданных: в `src/modules/media` нет `keepMetadata`, `keepExif`,
`withMetadata`, `withExif`, `withExifMerge`, `keepIccProfile`, `withIccProfile`
(статический тест). Тестовый JPEG с EXIF GPS собирается в тесте через
`withExif`. Проверка: `metadata()` варианта без `exif`/`xmp`/`iptc`/`icc`, а
побайтно нет `Exif\0\0`, XMP-пакета и GPS-тегов. Оригинал с GPS остаётся
приватным и никогда не выдаётся; его хранение и удаление — по существующим
правилам Media/Privacy.

## 7. Свежесть баз сигнатур: три состояния

Контроль даёт не «прошёл/не прошёл», а одно из трёх состояний. Сервис
вычисляет его из ответа `VERSION` (`ClamAV 1.5.4/<daily>/<дата сборки>`) по
серверным часам.

| Состояние | Когда | Ответ `OK` от `clamd` превращается в |
|---|---|---|
| `fresh` | официальная `daily` есть, возраст сборки ≤ 7 суток | `clean` |
| `stale` | официальная `daily` есть, возраст > 7 суток | `inconclusive` → карантин |
| `absent` | официальной `daily` нет (`VERSION` без версии базы) или ответ не разобран | `inconclusive` → карантин, **если нет явного исключения стенда** |

Ответы `FOUND` (`rejected`) и предельные эвристики (`inconclusive`) от
состояния не зависят.

**Исключение стенда при L1.** Переменная
`RECHARGE_MEDIA_TOOLS_DATABASE=stand-signatures-only` выставляется только
D1-gate и только при L1. С ней `absent` + `OK` → `clean`, но отсутствие
`daily` не выдаётся за пройденный контроль:

- `toolRevision` = `clamav-1.5.4/stand-marker-1/official-db-absent`;
- `health` → `database: {state:'absent', exemption:'stand-signatures-only'}`;
- отчёт D1-gate пишет «daily freshness: NOT APPLIED — official database
  absent (L1)», а не «passed»;
- статус D1 остаётся `Linux gate open`, пока не проверена официальная база.

Без исключения отсутствие `daily` даёт `inconclusive`. Это проверяется на
настоящем `clamd` с тестовой базой: исключение выключено → чистый буфер →
`inconclusive`, актив в карантине.

**Проверка правила 7 суток.** Unit-тесты разбора `VERSION` с управляемыми
часами: ровно 7 суток → `fresh`; 7 суток и 1 с → `stale`; `VERSION` без
`daily` → `absent`; нераспознаваемый ответ → `absent`; дата сборки в будущем →
`absent` (часы не согласованы, fail-closed). При L1 эти тесты — единственное
локальное доказательство правила; на реальной официальной базе оно
проверяется в Linux gate или при L2.

**При L2** после `freshclam` записываются версии `main`/`daily`/`bytecode`,
дата сборки, число сигнатур, результат `sigtool --info` и SHA-256 файлов
(`media-tools.lock.json`, раздел `databases`); исключение стенда не
используется; устаревание → `stale` и явная ошибка D1-gate. Обновление баз —
только вручную, по решению владельца.

## 8. Defender и EICAR: вариант A

`clamd` пишет принятый поток во временный файл в `TemporaryDirectory`
(`clamd/session.c:614` в теге `clamav-1.5.4`). Защита Defender в реальном
времени включена и, как ожидается, перехватит EICAR на диске; Storage-эмулятор
тоже хранит байты на диске. Решение владельца — **вариант A**:

- локально обнаружение и путь отказа доказываются собственной безобидной
  сигнатурой `Recharge.Test.Marker` — на уровне сервиса и по всему пути
  Storage. Это доказательство работы ClamAV **с тестовой сигнатурой**, а не
  обнаружения реального вредоносного кода;
- EICAR-тест пишется в D1 и является **обязательной** частью Linux gate;
  локально он пропускается с явной причиной «Defender real-time protection
  active»;
- локальный пропуск EICAR **не делает D1 зелёным**: итоговый статус D1 зависит
  от Linux gate (§12).

## 9. Матрица проверок

Все образцы создаются во время теста; EICAR собирается из частей только в
памяти и нигде не хранится в репозитории.

| Случай | Образец | Где ловится | Ожидание |
|---|---|---|---|
| EICAR | стандартная строка | `clamd` (Linux gate) | `rejected` → `blocked`; локально — пропуск с причиной |
| Сигнатура стенда | `Recharge.Test.Marker` в JPEG, по пути Storage | `clamd` | `rejected` → `blocked` |
| Подмена расширения | HTML и EXE-заголовок с `.jpg`; PNG, объявленный как JPEG | проверка байтов; формат после разбора | `signature_mismatch` / `rejected` |
| Слишком большой файл | > `maxBytes` | `confirmUpload` | `limit_exceeded` |
| Предел сканера | вложенность сверх лимита в полиглоте | `clamd` `AlertExceedsMax` | `inconclusive`, не «чисто» |
| Пиксельная бомба | PNG 30000×30000 с крошечным IDAT | заголовок + `limitInputPixels` | `rejected` |
| Бомба распаковки | PNG 20000×20000 из нулей (< 1 MiB) | те же лимиты | `rejected` |
| Повреждённый / обрезанный | JPEG и PNG, обрезанные посередине; битый заголовок | `failOn`, `AlertBrokenMedia` | `rejected`; `clamd` отмечает структурные повреждения (обрезку в заголовках, битые размеры сегментов JPEG, обрезанный PNG), а повреждения внутри сжатых данных JPEG и CRC PNG — только декодер |
| Polyglot | JPEG + ZIP с маркером; JPEG + HTML/JS в хвосте | `clamd`; перекодирование | `rejected`; в вариантах хвоста нет (побайтно) |
| Многокадровый | анимированный WebP | `pages` | `rejected` |
| Таймаут | `clamd`, который молчит (локальный TCP-сервер); конвейер дольше срока | сроки сервиса | `inconclusive` / `failed` → карантин |
| Сканер недоступен | `clamd` или сервис остановлен | адаптер | карантин; после запуска и повтора → `ready` |
| Переполнение очереди | больше заявок, чем «одновременно + ожидают» | приём сервиса | лишние сразу `503 busy`, без зависаний и накопления |
| Потолок памяти и освобождение после таймаута | самопроверка J1–J6 (§3.8) | Job Object, надзор сервиса | J1–J6 выполнены; отчёт `selftest-<время>.json` |
| Нет нативной сборки | загрузка без `@img/sharp-win32-x64` (подмена в тесте) | обработчик | `failed` |
| Устаревшая база | дата `daily` старше 7 суток по управляемым часам | разбор `VERSION` (unit) | `stale` → `inconclusive` |
| Официальной базы нет, исключение выключено | чистый буфер, настоящий `clamd` с тестовой базой | сервис | `absent` → `inconclusive`, карантин |
| Официальной базы нет, исключение L1 | чистый буфер | сервис | `clean` с `official-db-absent`; в отчёте «freshness NOT APPLIED» |
| Тестовая база не та или не загружена | подменённый файл; пустой каталог баз | `start` | отказ запуска, заявки не принимаются |
| EXIF/GPS | JPEG с GPS-тегами | обработчик | в вариантах нет метаданных |
| SVG | `<svg …>` и `<?xml …><svg …>` | байты, формат, загрузчик | `signature_mismatch` / `rejected` |

### 15.2 Стадия `inspect`

1. ClamAV 1.5.4 `.deb` для x86_64: SHA-256 из манифеста, GPG-подпись тем же
   ключом Cisco Talos (закреплённый коммит), распаковка `dpkg-deb -x` во
   временный каталог — без установки в систему.
2. `freshclam` (из того же `.deb`) один раз с отдельным `freshclam.conf`
   (`DatabaseDirectory` в пустом каталоге) и сторожем бюджета: лимит —
   меньшее из 400 МБ и остатка общего бюджета 700 МБ; при нулевом остатке
   `freshclam` не запускается. Сторож опрашивает каталог раз в 500 мс, а при
   выходе `freshclam` рост проверяется ещё раз при любом коде выхода — рывок
   между опросами тоже отклоняется. Затем итог журнала сверяется с общим
   бюджетом. Обязателен набор `main`, `daily`, `bytecode` — каждая ровно в
   одной форме `.cvd` или `.cld`. При превышении бюджета или неполном наборе
   каталог уходит в `_rejected`, и обе стадии падают до отчёта. Ту же проверку
   набора повторяют `inspect`, список открытых пунктов и запуск `clamd` в
   режиме `official`.
3. Для каждого `.cvd`/`.cld`: `sigtool --info` (версия, дата сборки, число
   сигнатур, проверка цифровой подписи), SHA-256, размер.
4. `sigtool --unpack` во временный каталог; перечень файлов; полный текст
   `COPYING` и любых файлов уведомлений (`COPYING*`, `LICENSE*`, `NOTICE*`,
   `README*`) — в отчёт. Отсутствие `COPYING` — явная строка «NOT FOUND».
5. Итог `inspect` — таблица версий/SHA-256 и тексты уведомлений; формулировка
   §3.5 «условия не опубликованы» заменяется результатом этой проверки.

### 15.7a Добавлено при реализации

- `media_tools_host.ts`: на Linux токены приходят в файле с правами 0600,

  по-прежнему `no`.
- EICAR через Storage идёт как член ZIP за JPEG: официальная сигнатура EICAR —
  хэш точного файла, а сам EICAR не прошёл бы проверку первых байтов при
  загрузке; `clamd` распаковывает ZIP.
- `stand-d1-gate.mjs` (Windows): каждый пропуск должен иметь одну из
  разрешённых причин (Defender для EICAR; «Linux gate only» для проверок с

  только пропуски «L1 only».
- `clamd_scan.test.ts` и `media_real_tools_flow.test.ts` получают режим базы
