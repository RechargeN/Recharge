## Этап 2 — архитектурный аудит

Прочитаны целиком все Accepted ADR (0011–0014), ARCHITECTURE_BASELINE.md, IMPORT_BOUNDARIES.md, SCENARIO_BUILDER_SPEC.md v1.3, SCENARIO_CONNECTED_PLANNING_SPEC.md, ROUTE_BUILDER_SPEC.md — на их основе код `apps/mobile/lib` проверен тремя параллельными агентами.

### Критичные находки

**1. Два параллельных домена "Scenario"** — самая серьёзная находка.
Нарушено: SCENARIO_BUILDER_SPEC.md §2 инвариант 1 («Scenario Builder расширяет Scenario в едином config-driven Create form engine, а не создаёт параллельный publish flow»); ADR 0011; ARCHITECTURE_BASELINE.md rule 10.
Канонический домен (days/items/legs/budget/capabilities, id-based item-source) — `features/create/domain/entities/scenario_draft_data.dart`, используется только внутри Create Hub. Легаси-домен `features/scenarios/domain/entities/scenario_draft_entity.dart` (`ScenarioDraftEntity`/`ScenarioStepEntity`, плоские `steps` без days/items/legs/id-identity) — отдельная top-level фича вне канонического списка 8 фич ARCHITECTURE_BASELINE, но при этом именно она — основная точка входа из `discover_hub_page.dart`, `discover_details_page.dart`, `discover_map_page.dart`, `search_page.dart`, `favorites_page.dart`, `profile_page.dart`, `notifications_page.dart` (через `RouteNames.scenarioBuilder`, `app_router.dart:94-96`).

**2. Идентичность по имени/категории вместо id (легаси Scenario).**
Нарушено: SCENARIO_CONNECTED_PLANNING_SPEC.md §2 п.5; SCENARIO_BUILDER_SPEC.md §2 инвариант 4.
`features/scenarios/application/controllers/scenario_builder_controller.dart:104-106` — дедупликация шагов по `category` вместо `objectId` (у `ScenarioStepEntity` нет полей `objectId/objectType`). Канонический `scenario_item_draft.dart` в `create/` делает это правильно.

**3. `packages/api_contracts` не используется вообще.**
Нарушено: ARCHITECTURE_BASELINE.md rule 2 («packages/api_contracts — единственный источник истины для DTO/API-клиентов»).
`lib/src/{contracts,dto,clients,serializers,generated}/` — только `.gitkeep`; `grep -rn "package:api_contracts" apps/mobile` → 0 совпадений (design_system — 4). Каждая фича определяет свои DTO самостоятельно (`create_draft_model.dart`, `event_draft_mapper.dart`, `auth_user_model.dart`, `discover_item_model.dart` и др.).

**4. Системное нарушение запрета cross-feature импортов.**
Нарушено: ARCHITECTURE_BASELINE.md rule 5; IMPORT_BOUNDARIES.md §2.
Прямые импорты между фичами как системный паттерн: `discover_hub_page.dart`, `discover_map_page.dart`, `discover_details_page.dart`, `favorites_page.dart`, `profile_page.dart` (14 импортов), `scenario_builder_page.dart`, `notifications_page.dart`. Обнаружен цикл: `discover_map_page.dart` ↔ `scenario_builder_page.dart`. Уточнение: в Этапе 1 `check-boundaries.ps1` дал «Boundary checks passed (suppressed by allowlist: 59)» — эти нарушения формально подавлены через `boundaries-allowlist.txt` (IMPORT_BOUNDARIES.md §6), т.е. это задокументированный legacy-долг, а не необнаруженные новые нарушения — но именно тот долг, который согласно политике должен сокращаться до нуля, а не расширяться.

**5. `core/errors/` отсутствует полностью — нет `AppException`/`Failure`.**
Нарушено: ARCHITECTURE_BASELINE.md canonical tree; ADR 0012 (error handling standard).
`core/` содержит только `config/`, `id/`, `telemetry/`. Общего `AppException`/`Failure` нет (`grep -rln "class AppException|class Failure"` → 0). Вместо этого — фиче-специфичные `AuthException`, `DiscoverException` (допустимое отклонение по ADR 0012, но базовой инфраструктуры для паттерна нет). `core/network/`, `core/storage/` тоже отсутствуют.

**6. `ProfileRoleTier.proGenerator` — отдельная доменная роль.**
Нарушено: ADR 0013 policy 5 («Starting roles: User, Creator, Admin»; Pro generator не отдельная роль).
`features/explore/application/profile_role_summary.dart:1-5` — `enum ProfileRoleTier { user, creator, proGenerator }`, персистентный enum-член наравне с user/creator, а не производный UI-label. `Admin` в этом enum отсутствует вовсе.

**7. Новые top-level директории вне замороженного дерева.**
Нарушено: ADR 0011; ARCHITECTURE_BASELINE.md rule 10.

### Ключевые находки с классификацией

**(d) Осознанный/задокументированный legacy-долг:**
- Два параллельных домена Scenario: канонический `create/domain/entities/scenario_draft_data.dart` (используется только в Create Hub) и легаси `features/scenarios/domain/entities/scenario_draft_entity.dart` (плоские steps, дедуп по `category` вместо id, до сих пор основная точка входа из Discover/Search/Favorites/Notifications/Profile). LAUNCH_STATUS.md сам явно называет P10-P60 записи (создавшие легаси-версию) "legacy runtime behavior... migration are separate cleanup work after stabilization" — это не тихий дефект, а признанный долг с планом, который просто ещё не выполнен.
- `quickPlan` в `CreateObjectType` — подтверждено независимо агентом: исключён из `rechargeCreateBlockConfigs`, обрабатывается отдельной legacy-веткой "read compatibility". Соответствует SCN-SB-02.
- Старые legacy enum-значения (`socialRequest`, `privatePlan`, `venue`, `bookableSlot`, `offer`, `announcement`) — не живые enum-члены, а только строки в compat-мапперах (`rechargeLegacyCreateTypeIds`), полностью замигрированы. Запись P62 в LAUNCH_STATUS, где они упомянуты как активные — просто более старая запись append-only лога, вытесненная более поздней `CAT-SYSTEM-MIGRATION-01`.

**(a) Реальные находки/расхождения с буквой спеки:**
- Канонический `ScenarioDraftData` не имеет собственного repository — персистится только через общий `CreateRepository.saveDraft/publishDraft`. SCENARIO_BUILDER_SPEC §5 прямо требует «собственный ULID, repository, lifecycle» — id есть, независимого repository/lifecycle нет.
- Favorites не ID-only — `FavoriteItemEntity` денормализует полный снимок (title/city/category/price/cover) в момент сохранения; id стабилен, но остальные поля — point-in-time копия, которая может устареть относительно исходного объекта. Ни один spec-документ (нет отдельного `S2_FAV_01` spec-файла) явно не называет это осознанным компромиссом.
- Роль Admin отсутствует в коде мобильного приложения вообще (`ProfileRoleTier` содержит только user/creator/proGenerator) — расхождение с ADR 0013 policy 5, хотя это может быть вне scope мобильного клиента (backoffice-функция).
- Capability-проверки существуют, но схлопываются в `ProfileRoleTier` до UI, а не проверяются гранулярно на каждое действие — частичная реализация паттерна.

## Этап 4 — аудит данных, persistence и миграций

Три параллельных агента проверили persistence-слой по всем ключевым агрегатам. Firebase нигде не предлагался как решение.

### Критичные находки (privacy/data leakage)

**1. Visibility fail-open.** При десериализации `EventVisibility`/`FindPeopleVisibility`/`VisibilityType` неизвестное/повреждённое значение молча деградирует в `public`, а не в `private`:
- `create_draft_entity.dart:314` — `VisibilityType.public` в `.defaults()`.
- `event_draft_data.dart:350` + `event_draft_mapper.dart:154-156` — `_enumValue(...) ?? defaults.visibility` (defaults = public).
- `find_people_draft_data.dart:313` + `find_people_draft_mapper.dart:263-265` — та же схема.

Воспроизведение: пользователь ставит `visibility: private` → данные повреждаются или enum переименовывается в будущем рефакторинге → `_enumValue` не находит совпадение по `value.name == name`, возвращает `null` → фоллбэк на `defaults.visibility = public`. Черновик, который пользователь считал приватным, становится публичным без его ведома. Контраст: `ScenarioCapabilitiesDraft` (`unlistedShare`, `publicPublish`, `scenario_draft_mapper.dart:849-850`) корректно fail-closed в `false`.

**2. Data leakage между пользователями через нескоупленные storage-ключи.**

| Datasource | Ключ | Скоупится по userId? |
|---|---|---|
| `create_local_datasource.dart:22` | `create_draft_$userId` | Да |
| `explore_local_datasource.dart:13-14` | `explore_profile_$userId`, `explore_settings_$userId` | Да |
| `notifications_local_datasource.dart:12` | `notifications_items_$userId` | Да |
| `auth_local_datasource.dart:13-14` | `auth.session`, `auth.user` | Нет (по дизайну — одна активная сессия) |
| `favorites_local_datasource.dart:10` | `favorites_items_v1` | Нет — глобальный |
| `discover_preferences_local_datasource.dart:23-25` | `discover.last_query`, `discover.saved_searches`, `discover.smart_search_history` | Нет — глобальные |

`AuthRepositoryImpl.signOut()` (`auth_repository_impl.dart:74-84`) чистит только `auth.session`/`auth.user` — ни один другой датасорс не очищается при выходе.

Воспроизведение (гипотетический multi-user сценарий): пользователь A сохраняет Favorite и поисковый запрос → logout (чистится только auth) → пользователь B логинится → B видит и может удалить Favorites и историю поиска A; create-draft/notifications/profile A корректно изолированы по userId, но не удаляются — зависают в хранилище. Оговорка: сейчас в моке существует только один демо-аккаунт (`demoUserId = 'demo_full_access'`), переключения между реальными пользователями физически нет — утечка сейчас не наблюдаема функционально, но 3 из 6 датасорсов уже правильно скоупились по userId, а 2 — нет, то есть это забытые места, а не единообразная политика.

### Реальные дефекты обработки повреждённых данных (необработанные исключения вместо graceful fallback)

- **`CreateDraftModel.fromJson`** (`create_draft_model.dart:483-484`) — `json['id'] as String` без fallback; датасорс ловит только `FormatException`. Частично повреждённый, но JSON-валидный черновик кидает необработанный `TypeError` при загрузке.
- **`AuthLocalDataSource.readSession()`/`readUser()`** (`auth_local_datasource.dart:23-30,39-46`) — `jsonDecode` без try/catch. Воспроизведение: записать в `auth.session` строку `"{not json"` → перезапуск → `restoreSession()` бросает необработанное исключение вместо тихого отката к гостю.
- **`DiscoverQuery` конструктор** бросает `ArgumentError` при `timeWindow != null && travelContext == null` (`discover_query.dart:34-36`), но `loadLastQuery()`/`ensureLoaded()` не перехватывают `ArgumentError`. Воспроизведение: `discover.last_query` содержит `time_window` без `travel_context` → необработанное исключение при открытии Discover.

### Legacy-классификация и таксономия — тихая потеря целостности

- **Legacy draft reclassification игнорирует свой контракт подтверждения.** `classify_legacy_planning_draft_usecase.dart` вычисляет `requiresUserConfirmation: true` (подтверждено тестом), но `create_draft_model.dart:638-647` использует только `classification.target`, флаг нигде не читается для показа диалога — legacy Quick Plan-подобный драфт молча становится каноническим `CreateObjectType.scenario` без спроса пользователя.
- **Осиротевший subcategory id.** `normalizeRechargeLegacySubcategoryId()` (`recharge_taxonomy_migration.dart:477-490`) при отсутствии соответствия возвращает сырой нормализованный вход как есть (не `null`/`'other'`/исключение). Воспроизведение: `updateSubcategory('legacy_totally_unknown_id')` → сохраняется как есть → категория нигде не резолвится → ранее заполненные критерии тихо теряются.

### Второстепенные находки

- `CreateDraftEntity.copyWith` не имеет параметра `organizerId` — поле нельзя изменить через copyWith (сейчас не используется).
- Отсутствующий `sourceObjectType` молча дефолтится в `ScenarioCatalogObjectType.place` (`scenario_draft_mapper.dart:398-420`) — искажение источника при повреждённых старых данных.
- `ScenarioDraftMapper._money` теряет `minorUnits`, если `currencyCode` отсутствует/пуст.
- Нет `==`/`hashCode` у `DiscoverQuery`, `DiscoverItemEntity`, `SavedSearchEntity`, `SmartSearchHistoryEntity`, `GeoPoint` — риск для тестов, не активный баг.
- `revision`/`expectedRevision` в Create/Scenario не проверяются при save/publish — поле есть, проверки нет.
- `publishDraft` заменяет `loc_*` для event/place/find_people, но не для `scenarioData` — не активно, публикация Scenario сейчас заблокирована раньше.

### Проверено и подтверждено корректным

- Координаты 56.9496/24.1052 — единственный канонический источник (`MarketConfig.riga`), реальной геолокации в приложении нет вообще — подменять нечего технически (N/A).
- Timezone/DST — не мок, реальная IANA tz-база с корректной обработкой весеннего "скачка" и осеннего "повтора".
- TravelTimeRepository — unknown корректно остаётся unknown.
- Scenario unknown/price (`MoneyEstimate`) — unknown≠0 соблюдается по всей цепочке.
- Enum↔id мапперы в Scenario — явные Map-таблицы, не `enum.name`.
- Favorites/Notifications round-trip — все поля физически сохраняются без потерь; проблема Favorites — логическое устаревание снапшота, не физическая потеря, не проявляется сейчас (мок-данные не меняются в рантайме).
- copyWith-ограничения на Discover/Favorites/Notification entities — намеренно узкая поверхность, не баг.
- Legacy id миграция таксономии (422→516) для распознанных id — корректна.

### Не Firebase-связанные, но требующие post-stabilization решения

- Logout не оркестрирует очистку non-auth датасорсов — замаскировано единственным демо-аккаунтом.
- Server-side optimistic concurrency поверх локального `revision`-поля — неприменимо без реального бэкенда.

**Реальные дефекты:**
1. Непоследовательная защита от двойного тапа при навигации по шагам Create Hub. `place_create_block.dart` дизейблит все кнопки навигации флагом `busy`; кнопки "Continue" в `event_create_block.dart:758,778`, `find_people_create_block.dart:1363,1376`, `scenario_create_block.dart:96,104` вызывают `await saveDraft()` без проверки статуса — быстрый повторный тап может запустить два параллельных сохранения.
2. `FavoritesController.toggleFavorite` (`:123-132`) читает `isFavorite()` из state до await, ничего не блокирует одновременные вызовы. В `discover_details_page.dart` три разных кнопки (app bar, action hub, bottom bar) вызывают один и тот же `_onFavoriteTap` без disable-состояния — воспроизводимо: быстрые двойные тапы дают дублирующиеся запросы.
3. `CreateController.ensureLoaded()` без try/catch — если `_loadCreateDraftUseCase` бросает исключение, оно не перехватывается, `CreateStatus.error` (используется в `create_page.dart:104`) остаётся мёртвым кодом — экран навсегда зависает на спиннере загрузки при любой ошибке загрузки.
4. `ExploreController.saveProfile()`/`_saveSettings()` — ни guard, ни try/catch; двойной тап "Сохранить" запускает параллельные записи (last-write-wins).

Чисто: mounted-проверки везде корректны; reload-on-revisit (`ensureLoaded`-паттерн) применяется единообразно; autosave/undo-redo в Create Hub работает правильно (50-записей bounded история, redo сбрасывается при новой правке); 400ms debounce для Route-логистики отсутствует, но это соответствует статусу RTE-05 "Planned" — честно нереализовано, не регрессия; PopScope/предупреждение о несохранённых изменениях нигде нет и нигде не требуется спекой — тоже не дефект.

### Критичные системные находки

**1. Happy-path-only fake-репозитории маскируют непокрытый error-handling (высокий риск).** В `favorites_controller_test.dart`, `notifications_controller_test.dart`, `create_controller_test.dart`, `explore_controller_test.dart` — фейки никогда не бросают исключение, хотя в проде есть `try/catch` (например `favorites_controller.dart:44-65`, `create_controller.dart:1674-1707`). **2. Инфраструктурный код без единого теста (высокий риск).**

## Этап 7 — security/privacy/configuration audit

Три параллельных агента проверили секреты/логирование/зависимости, auth/URL/десериализацию/ввод, и IDOR/ownership/visibility/Quick Plan. Формат находок — строго по требуемым 6 полям (entry point/preconditions/vulnerable path/impact/существующие ограничения/способ проверки), без выдачи гипотез за подтверждённые уязвимости.

### Подтверждённые находки с реальным (хоть и ограниченным) воздействием

**1. Visibility fail-open (at-rest дефект, impact ограничен отсутствием потребителей).**
- Entry point: повреждение JSON на диске (ручное редактирование secure storage на rooted-устройстве / будущий баг sync-логики / потеря поля при миграции схемы).
- Preconditions: значение `visibility` в сохранённом JSON отсутствует или не совпадает ни с одним известным enum-именем.
- Vulnerable path: `create_draft_model.dart:552` (`json['visibility'] as String? ?? 'public'`), `create_draft_model.dart:716-720` (`_parseVisibility` — `orElse: () => VisibilityType.public`), `event_draft_mapper.dart:154-156`, `find_people_draft_mapper.dart:263-265`.
- Impact: черновик, помеченный `private`, при повреждении данных восстанавливается как `public` в памяти. Для Scenario impact равен нулю — публичная публикация полностью заблокирована. Для Event/FindPeople publish физически работает, но нигде в Discover/ленте нет чтения `CreateRepository`/`publishStatus` — опубликованный объект никуда не рендерится другим пользователям. Итог: сейчас чисто at-rest дефект без наблюдаемого внешнего эффекта.
- Существующие ограничения: single-user mock, отсутствие backend-канала для публикации/показа контента другим.
- Способ проверки: записать вручную в secure storage под `create_draft_<userId>` JSON с `"visibility": "corrupted_value"`, перезапустить приложение, убедиться что `state.draft.visibility == VisibilityType.public`; убедиться, что дальше это никуда не транслируется наружу.

**2. AuthLocalDataSource/CreateLocalDataSource — необработанные исключения при десериализации (локальный DoS, не выше).**
- Entry point: старт приложения (`restoreSession()`) / открытие Create Hub (`loadDraft()`).
- Preconditions: значение по ключу `auth.session`/`auth.user`/`create_draft_<userId>` повреждено.
- Vulnerable path: `auth_local_datasource.dart:28-29,44-45` (без try/catch вообще); `create_local_datasource.dart:24-39` (ловит только `FormatException`, не `TypeError` от `create_draft_model.dart:483`).
- Impact: краш приложения (DoS). Не утечка данных, не обход авторизации.
- Существующие ограничения: повреждение требует уже скомпрометированного устройства (root/jailbreak с доступом к тому же UID).
- Способ проверки: чтение кода подтверждает отсутствие/недостаточность try/catch.

**3. Безусловная регистрация MockAuthRemoteDataSource — архитектурный факт, не активная уязвимость.**
- Entry point: экран входа.
- Preconditions: единственная реализация `AuthRemoteDataSource`, регистрируется безусловно (`service_locator.dart:110`), без dart-define/flavor переключателя.
- Vulnerable path: `auth_remote_datasource.dart:38-39` — жёстко закодированные `user@example.com`/`password123` выдают полный набор demo-capabilities.
- Impact: сегодня — архитектурный факт "нет реального auth-гейта", не "скомпрометированы данные других пользователей", поскольку прод-развёртывания с реальными пользователями не существует.
- Существующие ограничения: задокументированное состояние стабилизационного слайса (STAB-AUTH-FULL-ACCESS-01).
- Способ проверки: `flutter build apk --release` + вход с указанными кредами подтвердит выдачу полной сессии в release-сборке — важно зафиксировать как release-blocker перед реальным продом.

### Позитивные находки (проверенные защиты работают корректно)

- HTTPS-валидация контактов Place/Event реально enforced (`validate_place_draft_usecase.dart:387-390`, `validate_event_draft_usecase.dart:401-407`), включая защиту от userinfo-обфускации.

- Токены хранятся только через FlutterSecureStorage, без дублирования в открытом виде/логах.
- Секретов в tracked-файлах нет — `.gitignore` корректно исключает keystore/env/pem-файлы.

### Гипотетические/архитектурные риски на будущее

### Гигиенические риски (не security-находки)

- Placeholder Legal/Support/Privacy URL (`example.com`, TODO на релиз) — release-readiness gap, не угроза.

Ничего из найденного не меняет общие выводы финального отчёта (`финальный_отчет_аудита.md`), но добавляет 15 новых конкретных находок, преимущественно в категориях "документ противоречит документу" (G-01…G-04) и "governance-документ описывает несуществующую инфраструктуру, но помечен Done" (G-11…G-13) — это системный паттерн: несколько раз статус "Done" в LAUNCH_STATUS относится к написанию политики, а не к её соблюдению в коде.
